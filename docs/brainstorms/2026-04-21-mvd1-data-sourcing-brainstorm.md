# MvD_1 data sourcing under `$download_data=0`

## What We're Building

Make `outputs_stata_code/MvD_1_macro.do` work out of the box on a fresh clone with the repo's default `$download_data=0`. Three external series are currently downloaded from dbnomics/CBO/OECD on every `$download_data=1` run and `use`d from `outputs_stata_code/data/*.dta` afterward — but those `.dta` files are neither committed nor regenerated by any other script, so default runs fail at `r(601)` on the first `use data/irr_data.dta`. Closes §14.5-P3 in the stata pipeline audit.

## Why This Approach

The §14 audit uncovered that MvD_1's three download blocks are the only reason MvD_1 fails under the default `$download_data=0`. A short survey of dbnomics calls across the repo shows one partial duplication (`GGDC Penn irr.USA` is downloaded by both M04 and MvD_1) and two genuinely unique series (CBO SS benefits, OECD working-age population × Penn avh+emp). The duplication is small enough that a targeted fix beats a full pipeline restructuring. The broader "single source of truth" question is deferred — the existing "each module owns its own committed snapshot" pattern works for inputs and is simple to extend to MvD_1.

## Key Decisions

**Revision (2026-04-22, user correction):** keep MvD_1's code as written. Each `.do` that needs a dbnomics series should re-run its own download; that is the "original code" pattern for this repo. Do NOT reach across into M04's `irr.dta` — the minor duplication of the raw download is accepted in exchange for keeping MvD_1 self-contained and matching the style of the inputs scripts (each owns its snapshot).

- **All three MvD_1 series: commit processed `.dta` as frozen snapshots.**
  Bootstrap once in Stata with `$download_data=1` via `__replication_graphs.stpr`, commit the resulting `outputs_stata_code/data/irr_data.dta`, `outputs_stata_code/data/benefits_cbo.dta`, and `outputs_stata_code/data/avghours_data.dta`. No source-code changes to MvD_1. Matches the inputs pattern (`depreciation/depreciation.dta`, `tfp/gamma.dta`, `social_security/contributions.dta`, `sensitivity_stata_code/exog_rate/irr.dta` — all committed frozen downloads next to their producing script).

- **`$download_data=0` stays the default.** Matches the inputs pipeline's default; keeps replication reproducible without network.

- **Broader structural refactor deferred.** No central `data/raw/`; no cross-pipeline coupling. Each module keeps its own local committed snapshot. The fact that M04 and MvD_1 both cache `GGDC Penn irr.USA` is accepted as the cost of self-contained scripts. §14.5-P3 closes once the three `.dta` files land.

## Open Questions

- Bootstrap step must be run in Stata manually (default workflow: double-click `.stpr`, run `MvD_1_macro.do` with `$download_data=1` set in the Command window). The plan will include the exact preamble. This turns into `c5` (commit the `.dta` snapshots after the user runs the bootstrap).
- `outputs_stata_code/data/` doesn't exist on disk yet. Stata's `save` does NOT create parent dirs. Plan should include a `capture mkdir data` line at the top of MvD_1 as a one-line safety net.
